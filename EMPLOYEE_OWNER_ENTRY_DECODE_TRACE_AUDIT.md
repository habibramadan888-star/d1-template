## Why Owner History Shows 2030

The owner history frontend maps cloud rows through `normalizeLedgerSession(...)`.

If `export_text` is present, `normalizeLedgerSession` calls the legacy `parseTXT(raw)` parser before trusting the stored session summary.

The stored `export_text` is the newer employee-entry export format, not the old owner TXT handover format. The legacy parser does not understand these employee sections:

- `==== CASH RECEIVED ====`
- `==== ARREAR REPAID ====`
- `==== TRANSFER ====`
- `==== ARREARS OPENED ====`
- `==== HANDOVER ANCHORS ====`
- `==== SUMMARY ====`

Local reproduction with the live `export_text` and current owner parser produced:

| Parsed Row | Parsed As |
|---|---|
| `Entries: 4` | cash row, amount `4` |
| `Exported 2026-07-03T...` | cash row, amount `2026` |

Owner parser result:

| Metric | Value |
|---|---:|
| parsed entry count | `2` |
| parsed cash total | `2030` |
| parsed gross total | `2030` |

Conclusion: `2030` is generated by the owner frontend decoder, not by the D1 session summary.

## Why Detail Has No Complete 4 Rows

There are two separate issues:

1. The three normal `transactions` rows for the restored session still have `status = VOID` and `voided_at` set from the previous delete action. The earlier restore only restored the `sessions` row, not the associated detail rows.
2. The bed transfer event exists in the event trace as a bed transfer event with amount 50, but it is not stored as an active `transactions` row under this session.

Because `/api/session_detail` reads active `transactions`, it returns no active detail rows for this session.

## Root Cause Classification

Primary classification: `OWNER_HISTORY_SUMMARY_DECODER_WRONG`

Secondary contributing issue: `D1_STORED_ENTRIES_MISSING`

Reason:

- The owner visible total `2030` is caused by the owner frontend reparsing employee `export_text` with the legacy TXT parser.
- The missing detail is caused by missing active structured entries for this session: no `entries_json`, no active transaction rows, and bed transfer stored outside the transaction detail path.

## Recommended Smallest Fix

Do not change parser or financial formulas.

Smallest safe fix:

1. Owner history list should trust structured session summary fields for `source in ('EMP','employee_entry')` instead of reparsing employee `export_text` with the legacy TXT parser.
2. Owner history detail should support employee-entry detail by reading active structured entries from the correct sources:
   - `transactions` for rent / arrears payment / deposit / expense / checkout rows.
   - bed transfer event/anchor source for bed transfer rows, or ensure future bed transfers also materialize into the session detail contract.
3. For the already-restored `S20260703-amv7l`, any correction of associated transaction void status or bed transfer materialization would be a separate approved production write. It was not performed in this read-only audit.
4. Add a guard so `export_text` from employee-entry format is displayed as readable text only, not used as the authoritative numeric source for owner history cards.
