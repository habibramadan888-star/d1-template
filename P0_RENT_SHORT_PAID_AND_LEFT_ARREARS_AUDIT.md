## Scope

This audit traces why a Rent short_paid entry for bed 144 did not remain visible as open Cloud Arrears, and reviews the current Left With Arrears form against the intended business fields.

No code was changed. No deployment was run. No production data was written.

## Executive Summary

The bed 144 Rent short_paid anchor was generated and uploaded. It was also materialized into `arrear_tasks`.

The current open Cloud Arrears lookup returns no item because the latest short-paid task was marked `PAID` with `actual_received = 1400`, even though the intended arrears amount was only `70`. This happened after two active Rent rows for the same bed and same rent period were uploaded at the same timestamp:

- `S20260706-8uzsv`, transaction `ent20260706-8uzsv-01`, paid `700`
- `S20260706-8vgnq`, transaction `ent20260706-8vgnq-01`, paid `700`

The backend short-paid reconciliation sums all active Rent `paid` for `bed + period_start + period_end`. With two active duplicate Rent rows, total paid became `1400`, which is greater than the `period_due = 770`, so the Cloud Arrears task was closed as paid.

Primary root cause:

`DUPLICATE_SESSION_DEDUPE_BUG`

Secondary cloud lookup cause:

`ARREARS_CREATED_BUT_STATUS_WRONG`

The Left With Arrears form is currently built inside the generic Checkout form. It contains several manual fields that should be system-read, and it is missing one required business field: `confirmed_not_returning_date`.

Primary Left With Arrears form root cause:

`LEFT_WITH_ARREARS_REUSES_GENERIC_CHECKOUT_FORM`

## Backend Behavior Causing The Closure

In `handleEmployeeEntry()` the Rent short-paid branch:

1. Inserts the current transaction.
2. Queries total paid from all active Rent transactions for the same `corpid + room + period_start + period_end`.
3. Computes `remain = periodDue - totalPaid`.
4. Creates or updates an `arrear_tasks` row if `remain > 0`.
5. Closes the existing task as `PAID` if `remain <= 0`.

This design allows a duplicate Rent upload for the same bed/period to look like a real second payment. In the current data, two active 700 AED Rent rows for bed 144 and period `2026-08-01 -> 2026-09-01` make the summed paid value `1400`, so the 70 AED Cloud Arrears row is closed.

## Root Cause Classification

Rent short_paid root cause:

The short-paid anchor and arrears task exist, but duplicate active Rent rows caused the task status to become `PAID`, so the employee and owner open-arrears lookups correctly filter it out.

## Recommended Smallest Fix Order

1. Fix Rent short-paid Cloud Arrears reconciliation so duplicate active sessions do not mark a short-paid task as settled. Use session/entry identity and explicit repayment anchors, not summed duplicate Rent rows alone, to close Cloud Arrears.
2. Add session-level duplicate guard or same-ticket upload guard for identical `bed + period_start + period_end + paid + operator + timestamp/attempt` rows while preserving legitimate repeat uploads as new sessions.
3. Ensure production schema supports structured `sessions.entries_json` / `summary_json`, or keep treating `export_text` anchor JSON as the production read source until a controlled migration is approved.
4. Update employee Arrears Payment empty state to show latest closed/voided reason when no open task exists, including `Last arrears was settled or voided`.
5. Split Left With Arrears into a focused Checkout sub-form with only required employee fields plus read-only system context.
6. Add `confirmed_not_returning_date` to Left With Arrears UI payload and validation.
