# Owner Arrears Infinite Loading Root Cause

Root cause classification: `ABORT_NOT_HANDLED`, `DUPLICATE_FETCH_RACE`, `TTLOCK_AGGREGATION_BLOCK`, `API_TIMEOUT`.

| Step | Function / API                          | Expected                                                   | Current                                                                 | Root Cause                    | Fix                                                                            |
| ---- | --------------------------------------- | ---------------------------------------------------------- | ----------------------------------------------------------------------- | ----------------------------- | ------------------------------------------------------------------------------ |
| 1    | `loadArrearsForOwner()`                 | Loading always closes to success, empty, error, or timeout | Abort path could return after re-rendering skeleton                     | `ABORT_NOT_HANDLED`           | Latest abort now becomes retryable timeout/error state; stale abort is ignored |
| 2    | `/api/arrears/followup/tasks?limit=...` | Bounded request and limited rows                           | Primary request used a long timeout budget                              | `API_TIMEOUT`                 | Request now uses `ARREARS_FETCH_TIMEOUT_MS=10000` total budget and `limit`     |
| 3    | `/api/arrears?limit=...` fallback       | Fallback must not double total wait                        | Fallback could add another long wait                                    | `API_TIMEOUT`                 | Fallback consumes only the remaining timeout budget                            |
| 4    | TTLock hydration                        | Must not block first paint                                 | TTLock aggregation could run after first paint but lacked short timeout | `TTLOCK_AGGREGATION_BLOCK`    | TTLock card hydration now uses a 3s timeout and remains background-only        |
| 5    | Duplicate fetch                         | Older request cannot overwrite newer UI                    | Sequence guard existed but latest abort still showed skeleton           | `DUPLICATE_FETCH_RACE`        | `arrearsLoadSeq` is retained and status is closed in `finally`                 |
| 6    | Empty/error state                       | User must never wait forever                               | Standalone skeleton had no retry timeout state                          | `MISSING_FINALLY` / `UNKNOWN` | Overview arrears section has explicit empty, error, timeout, retry states      |
| 7    | API contract                            | Renderer fields must match API                             | Contract mostly matched after prior fix                                 | No current mismatch found     | Regression test locks API/UI fields                                            |
| 8    | Auth / readonly_admin                   | Read-only branch must not hang                             | No auth branch hang found in static path                                | Not root cause                | Kept read-only UI behavior and backend 403 write guard                         |

Conclusion: the visible 3-minute loading was caused by abort/timeout paths that could leave the user-facing module in skeleton state, combined with duplicate request races and long fallback budgets. The fix closes the state machine and moves arrears into an isolated overview module.
